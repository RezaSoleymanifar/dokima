No tests were written or run, because a split carries none until each child is planned on its own.

**The stories** (each has five criteria and depends only on story 1, so main keeps working after each one lands):
1. **On and off:** `/autopilot start` and `/autopilot stop` from a code owner switch an issue and everything under it, on an issue or its PR. An Autopilot pill shows on the board. The commands start no stage by themselves.
2. **Approved plan starts the worker:** on autopilot the worker starts without waiting for `/work`, and an approved split gets filed the same way. The river still stops, mentions the owner and sets Needs you on questions, an escalation, three blocks in a row, a rejected hand-back or a failed run.
3. **Approved PR merges:** it merges once the reviewer approves and every required check is green. A PR that changes a workflow file still waits for the owner, and a refused merge stops with GitHub's reason.
4. **Children start when their blockers merge:** a child starts planning once everything blocking it has merged, and children with nothing to wait on run in parallel.
5. **Autopilot ends by itself:** when the last child closes, the parent closes, autopilot switches off and the pills clear.

**Questions for the owner** (each child is planned on the stated assumption until they answer):
- **Merging without the owner's approval:** should the reviewer's approval stand in for the owner's? AGENTS.md says the owner approves and merges, and the bot can't approve. I assumed yes: `/autopilot start` hands that merge approval to the river.
- **Work already waiting:** should `/autopilot start` pick up what's already waiting, like an approved plan or PR? I assumed it does.
- **Where it applies:** said on a child issue or a PR, does it cover only that issue and what's under it, or the whole tree? I assumed only that issue and what's under it.
