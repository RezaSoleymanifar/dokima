**Why split:** the issue has four separate goals, and together they need far more than five criteria. Each story can merge on its own and main still works.

**The stories:**
1. **One manifest in code** lists every label, board field and option, view, required check name, branch rule and app permission Dokima needs. A test fails when code uses a setting the manifest leaves out. The manifest's permissions must match `dokima/app.json`. Waits on nothing.
2. **The audit and its report.** The audit compares the manifest with the repo's live settings and writes one plain line per difference. The report goes on one pinned Setup issue, marked Needs you, and later runs update that same issue. It mentions only this repo's code owners. `app.json` gets read-only Administration. Anything GitHub won't show, such as branch rules before that permission is granted, is listed as "could not verify" and never shown as fine. Waits on story 1.
3. **Auto-fixes.** The audit adds missing labels, board options and views itself. It only reports permission and branch rule differences, and it never renames or deletes anything that already exists. Waits on story 2.
4. **Triggers.** A workflow runs the audit daily, after label or branch rule changes, and on request, with runs queued one at a time. Waits on story 2.
