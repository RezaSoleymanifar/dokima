**User story:** The owner sees a card within seconds of every command and every hand-off. It says so when the run is waiting its turn, and each run keeps that one card until it becomes its record.

**Acceptance criteria**
- **186.1** A code owner's `/plan`, `/work` or `/review` puts up a card saying queued for that stage. It goes on the issue, or on the PR for the worker and code review once there is one. The run then turns that same card into its record and posts nothing else.
- **186.2** When a run waits behind another run on the same issue or its PR, its card says waiting and links that run. A run with nothing ahead of it says queued, not waiting. Once the run starts, its card stops saying waiting.
- **186.3** Every stage gets the same card, and so does every hand-off the river starts by itself. Filing a split uses one card too: it becomes the "Split filed" record, or says why the filing failed.
- **186.4** (non-functional) Only a code owner's command posts a card. A stranger's command, or an owner comment that isn't a command, posts nothing.

**Tests** are all in the new `tests/test_live_queue.py`:
- **Commands:** the test runs the listener (`commands.yml`) and then `agent.yml` with exactly the inputs the listener hands over. It checks GitHub between the two, before the run has started, for all four stages, including the two cards that belong on the PR.
- **Waiting:** these cases fake another run (run 41) whose card is up while GitHub reports it as in progress or queued. It is on the issue in one case and on the PR in another. Two cases must *not* say waiting: run 41 has already finished, or no other run exists. A hand-off made while run 41 is going is covered too.
- **Hand-offs:** a plan review that blocks hands back to the planner, and a worker that passes hands on to the code review on the PR. Each next run is replayed from the exact signal that was sent. Filing a split is covered when it succeeds and when GitHub refuses it.

The test file also sets one technical choice for the worker: the run being waited for is found from an earlier card on the issue or PR, plus GitHub saying that run hasn't finished.

**One older test changed:** the "owner's `/plan` posts nothing" case in `test_start.py::test_a_failed_command_says_why_and_stops_for_the_owner` now expects exactly one queued card. The reason is recorded in the plan.
