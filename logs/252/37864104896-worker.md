**What happens when the reviewer approves a plan** (in `dokima/agent.py`, the step that decides what follows a run):
- **Recording:** each "blocked by" link becomes GitHub's own blocked-by link on this issue, and each "blocks" link goes on the other issue as blocked by this one. Links GitHub already has are not added twice. Links the previous approved plan had and the new one dropped are removed first, so turning a link around doesn't count as a loop. A link a person made by hand is never removed.
- **Loops:** before writing anything, code follows GitHub's blocked-by links. If the plan would make issues block each other, directly or through other issues, nothing is recorded and the river stops for the owner, naming every issue in the loop.
- **GitHub errors:** if GitHub can't be read, or refuses or fails to add or remove a link, the river stops and the issue gets that link and GitHub's own words. On autopilot the worker does not start.
- **Where links come from:** only the newest planner record that the bot posted and that passed its check. Links in a review, a rejected hand-back or a record someone pasted are never used.
- **Cards:** when a link is added, dropped or changes kind, code redraws the card of this issue and of every issue involved. A plan the reviewer blocks changes nothing.

**How the other issue's card shows the link** (in `dokima/card.py`): there is no GitHub "relates to" link and no comments are allowed, so I add a hidden list in the code-owned card part of the other issue, naming the issues that link to it. It is only a list of where to look. Each time the card is redrawn, the links themselves are read from those issues' approved plan records, so editing the hidden list can't make a false link show. That's why the link is still there when the card is redrawn later.
