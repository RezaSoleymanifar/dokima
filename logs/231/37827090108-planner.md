**Why I split it:** your comment added two things: the links on the planner's run comment, and GitHub's own blocked-by links recorded once the plan passes review. That brings the issue to seven criteria (rule R2 allows at most five). The GitHub links also go into the autopilot code, which is unrelated to the pack and the checks (rule R3).

1. **The planner finds the links and code checks them.** The planner's starting pack lists every open issue, its prompt asks for the three kinds of link, and its hand-back has a `links` field. The check rejects links that are missing or malformed, a number that isn't an open issue, and an issue linked to itself. If GitHub can't list the open issues, the run fails instead of going on with an empty list. Depends on nothing.
2. **Both cards show the links.** The card on the issue and its pull request, and the planner's run comment, each show Blocked by, Blocks and Relates to with an icon of its own. Depends on story 1.
3. **Code records the links on GitHub once the plan passes review.** Blocked-by and blocks links become GitHub's own blocked-by links on both issues. Only code writes them, never the model, and a link GitHub refuses stops the river and says why on the issue. Depends on story 1.
