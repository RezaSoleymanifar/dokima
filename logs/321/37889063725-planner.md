**Agent:** I split issue #321 into four stories instead of writing one plan. The issue asks for seven kinds of numbers plus three rules for the page, which is more than five criteria (split rule R2). The hand-back is in `/tmp/dokima-out/plan.json`, and both checks pass after I shortened a few sentences that ran over the word cap.

**The four stories:**
1. **The page itself, refreshed on its own, showing what shipped.** It's one pinned issue titled Insights, drawn by code, linked from the board's description and refreshed every 15 minutes and on the Run workflow button. It shows issues closed and pull requests merged for Today, Last 7 days and All time, and a 30-day burndown chart of open issues. Its first line says when it last refreshed. If GitHub refuses a read, the run fails naming what it couldn't read and leaves the page as it was. Labels pass the repo's word check and tables have at most four columns, so it reads on a phone. The other three stories each add a section to this page and depend on it.
2. **Cost.** Tokens, agent time and API cost split by planner, worker and reviewer; average cost and agent time per merged pull request; the five most expensive issues; and a count of runs that have no stats. Only the bot's own run records count. These numbers come from the stats each run record already stores (`report` in `dokima/agent.py`).
3. **Reviews and lead time.** How often plans and pull requests pass review first time, the average rounds until approved, and the median and longest time from issue opened to merge. A period with nothing to count shows a dash.
4. **What waits on you and CI health.** Every question and Needs you waiting now, with how long each has waited; the median wait for ones you answered; failed Actions runs; and whether main is green. If GitHub can't report main's checks, the page says "unknown", never green.

**Questions for you.** Each story is planned on the assumption shown:
- **Where the page lives:** a pinned issue, like the Setup issue, rather than a GitHub Pages site. It needs no new setting and opens in the GitHub phone app.
- **What counts as "today":** UTC, and the page says so.
- **How far back the burndown goes:** the last 30 days.
- **When a wait on you ends:** at your next comment or review on that issue or its pull request. GitHub keeps no history of the Needs you pill, so it can't be timed directly.

It's linked as related to #121 (the board's own Insights charts) and #297 (when Needs you shows).
