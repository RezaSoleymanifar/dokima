**Why it's a split now:** your later `/plan` comment added two asks. One is that the planner and the worker report found issues too. The other is that the planner's links are written by the same checker. That makes two separate goals and more than five criteria, which is the rule for splitting.

**Story 1: issues any agent finds are filed, parked and labeled `filed-by-dokima`.**
- The planner, the worker and the reviewer each list found issues in the same hand-back field.
- Each found issue is filed in that agent's own run, labeled `parked` and `filed-by-dokima`, even on a repo that doesn't have those labels yet.
- Each filed issue says where it was found and by which agent, gives the finding's reason and evidence, and links the record of the run that found it.
- A filed issue gets nothing more: no sub-issue, no blocked-by link, no autopilot, and no stage starts on it.
- The same finding is never filed twice. Titles are compared ignoring letter case and spacing, including issues already closed.
- The run's card names each filed issue by its number and no longer calls them proposals. If GitHub refuses to file one, the card says which one and gives GitHub's reason.
- Filing happens only after the existing end-of-turn check passes, so a rejected hand-back files nothing. There is no new workflow, job or command.

**Story 2: the planner's links are written by the same checker.** It waits for story 1.
- "Blocked by" and "blocks" become GitHub's own blocked-by links.
- GitHub has no built-in "relates to" link, so that one becomes a cross-reference you see on both issues.
- A rejected plan writes no links. The planner's card names each link it wrote, or GitHub's reason when one is refused.

**How I read "the checker does it":** the check step runs with no GitHub key, by design. So I read it as "the same run's existing code, right after the check passes, using the key made once the agent has finished". It's a stated requirement in story 1, not a question to you.
