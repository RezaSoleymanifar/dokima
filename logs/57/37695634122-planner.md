**Feature:** PRs never sit stale behind main.

1. **Open PRs are brought up to date after every merge to main.** Unchanged from the first split:
   - After each merge, GitHub's own Update branch runs on every open PR that's behind, drafts included.
   - PRs already up to date get no update.
   - When GitHub refuses an update, that PR gets one comment with GitHub's reason, and the other PRs are still updated.
   - The update uses the Dokima app's token, so the PR's checks run again. It won't overwrite a PR that was pushed to in the meantime.
2. **A clash with main goes to the planner, on the record.** Rewritten from "goes to the worker". Depends on story 1.
   - The bot posts one record on issue N naming the merge that caused the clash (its commit, and its PR if there is one) and every file that clashed.
   - The planner then starts right away, with no command from you. The clash starts no worker.
   - For a PR Dokima didn't build, no agent starts. The PR gets a comment naming the merge and the files that clashed, and pings you.
3. **Queued PRs are retested on the latest main before merging.** Unchanged:
   - The all-tests check and the per-criterion checks also run in GitHub's merge queue.
   - In the queue they find the PR's issue from the queue's branch.
   - A queued PR with no linked issue fails with the same reason it gives on a PR.
   - Pull request checks and repos without a queue are unaffected.

I added three requirements to story 2 that you didn't ask for directly:
- **The worker after a re-plan:** today the worker merges main as its first step and fails if anything clashes. Once the planner re-plans and you say `/work`, the worker would stop dead there. The story makes the worker get past that and push a branch with main merged in and no conflict markers left.
- **The fence:** the fence must never undo main's own changes that come in with that merge.
- **Repeated merges:** more merges while the planner is queued or running must not start a second planner run for the same issue.
