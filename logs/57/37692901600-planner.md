**Agent:** I've handed back a split of issue #57 into three stories rather than a single plan, because the owner's 2026-10-07 comment ("Hybrid…") added two goals to the original ask. Each goal touches a different part of the code. Both checks pass on `/tmp/dokima-out/plan.json`, and no test files were written, since a split carries no tests.

**Why it's split:**
- **R1:** there are three independent goals.
- **R3:** they live in unrelated code: a new updater workflow, the worker's start in `agent.yml` plus `dokima/fence.py`, and the checks in `done-whens.yml`, `full-suite.yml` and `dokima/checks.py`.
- **R2:** together they need about ten criteria.

Each of the issue's promises goes to exactly one story.

1. **Open PRs are brought up to date after every merge to main** (no dependencies).
   - When main changes, GitHub's own "Update branch" runs on every open PR that is behind, drafts included.
   - PRs that are already up to date are left alone.
   - If GitHub refuses an update, that PR gets a comment saying why, and the other PRs still update.
   - The update must use the Dokima app's token. An update made with the workflow's built-in `github.token` starts no workflows, so the PR's checks would not run again.
   - The update must also pass the PR head it read, so a push that lands in between isn't updated over.

2. **Clashes with main go to the PR's worker** (needs story 1).
   - A clash on a Dokima PR (branch `try/issue-N`) starts that issue's worker by itself.
   - That needs a fix: today the worker's first step merges main, and a clash fails the whole run, so a clashing PR can't be handed to its worker yet.
   - The worker's pack lists the clashing files, and the fence must not drop main's own changes as out of scope.
   - A clash on a PR Dokima didn't build starts nothing; it gets a comment that mentions the owner.
   - Further merges while that worker is queued or running don't start more worker runs.

3. **Queued PRs are retested on the latest main before merging** (no dependencies).
   - The all-tests check and the per-criterion checks also run when a PR is in GitHub's merge queue. They don't today, so the queue would wait forever for checks that never come.
   - In the queue, the criterion checks find the PR's issue from the queue's branch name.
   - A queued PR with no linked issue fails the gate with the same reason it gives on a normal PR.
   - Checks on normal PRs behave exactly as before.

Each story carries the context I found (file paths, the GitHub API calls, the rules that limit what the bot can do), so its own planner doesn't have to research it again.
