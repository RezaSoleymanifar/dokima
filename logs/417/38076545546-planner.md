**What I found:** the problem is real. In `.github/workflows/agent.yml:372`, any GitHub error inside `python3 -m dokima.agent next` is turned into a plain stop (`|| NEXT=stop`), and nothing is added to the record. The fix fits in `dokima/agent.py`, so no workflow file needs to change.

**Criteria:**
- **417.1:** When GitHub refuses a call while deciding what runs next, the record gets one line with GitHub's reason and no stage starts. A run GitHub answers gets no such line.
- **417.2:** When the refusal is GitHub's rate limit (GraphQL or REST), the step waits until that limit's reset time, then starts what it would have started, with the same Next line as a normal run. Any other refusal is reported at once, with no wait.
- **417.3** (non-functional, fail closed): a decision that still fails stops for you. The Next line mentions you and the card shows Needs you.
- **417.4** (non-functional): the step waits for the rate limit at most once, then stops. It never retries in a loop or hangs.

**Tests**, in `tests/test_next_rate_limit.py`: they run `next` on a passed planner record against a fake GitHub and a fake clock, so a wait of up to an hour takes no time. The fake fails every call until the reset of whichever limit ran out. A fix that never retries, retries too early or waits on the wrong limit fails the tests.
