**Agent:** I fixed the reviewer's blocker (R5): in both cases it found, an agent's words no longer make GitHub draw HTML. All 12 of the plan's tests in `tests/test_code_as_written.py` pass locally. GitHub's own check results don't exist yet.

**What was wrong:** `escape_words()` in `dokima/card.py` guessed which backticks GitHub would treat as code. It guessed wrong in two places:
- **A backtick inside a link's address.** GitHub reads the address first, so the backtick doesn't start code there. Dokima thought it did, and left the words after it unescaped.
- **A raise's label.** The label and the raise's words are escaped separately but drawn on one line. A lone backtick in the label could pair with a backtick in the words.

**The fix** (`dokima/card.py`), as the reviewer suggested. Outside code:
- A backtick that never closes is now written as a character code (`&#96;`) instead of a raw backtick, so nothing next to it can pair with it.
- Every `[` is now written as `&#91;`, so GitHub never sees a link that could take a backtick away from the code it belongs to.

**Side effect to decide on:** a markdown link written in an agent's words now shows as plain text, not a clickable link. On main those links work. This keeps things fail closed, but it's a visible change, and only you can accept it with your Approve on the pull request. I noted it in `work.json` but didn't raise it, because a worker can't send questions to you.

**Recorded rendering:** I rebuilt `dokima/github_rendering.json` from scratch by asking GitHub how it shows what the code writes now. It holds only the 8 texts the tests ask about, and none of them draws a `<kbd>` tag.
